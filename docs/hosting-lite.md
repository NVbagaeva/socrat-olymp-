# Свой сервер в Москве за 350–700 ₽: облегчённый набор вместо полного Supabase

Этап 0, проверка до покупки. Отчёт от 12.10.2026. Ничего не куплено и не
настроено. Сервер, DNS, Timeweb и облачный Supabase я не трогал.

Проба этапа 0 жила в `infra/lite-probe/`. На этапе 1 она стала боевым
набором `infra/lite/`, а её сценарий — проверкой
`infra/lite/test/scenario.mjs` в workflow `lite-server.yml`. Как
пользоваться сервером — [docs/SERVER.md](SERVER.md).

## 1. Короткий итог

- **Облегчённый набор работает с сайтом без единой правки кода.** Это
  PostgreSQL, GoTrue, PostgREST и Caddy. Тот же `supabase-js` 2.117.3, что
  в сборке сайта, прошёл из браузера весь сценарий PR #174: 34
  проверок, ни одной ошибки. SQL пробного кабинета
  (`supabase/trial/auth_trial.sql`) применяется как есть, письма идут
  по нашим русским шаблонам.
- **Память: 1 ГБ запускается, но запаса в 25 % нет — нужно 2 ГБ.**
  Четыре контейнера в пике занимают 145–149 МиБ. В худшем случае, когда
  буферы базы заполнены целиком, — 264–271 МиБ. Вместе с Docker
  (~210 МиБ) и самой Ubuntu 24.04 (~300 МиБ) выходит около 780 МиБ из
  примерно 960 МиБ, доступных на сервере «1 ГБ». Это запас около
  19 %. Добраться до 25 % можно, только урезав Ubuntu, и любой новый
  сервис (Storage) этот запас съест. На 2 ГБ запас около 60 %.
- **Рекомендация: FirstVDS, тариф «Старт» NVMe — 1 ядро, 2 ГБ, 40 ГБ,
  599 ₽ в месяц, Москва.** Это укладывается в бюджет, IPv4 входит в цену,
  тариф меняется без переустановки. Набор на 1 ГБ (RUVDS «Старт Хит
  SSD», 349 ₽) технически запускается, но условие о запасе не выполняет;
  не советую.
- Timeweb Cloud в Москве стоит 1380 ₽ за 1 ГБ и 2140 ₽ за 2 ГБ (с IPv4),
  то есть вдвое дороже потолка бюджета.

## 2. Что такое облегчённый набор

| Сервис | Образ | Зачем | Память в пике* |
|---|---|---|---|
| PostgreSQL 17 | `postgres:17-alpine` | база: аккаунты, профили, коды комплектов | 47 (166 с полными буферами) МиБ |
| GoTrue | `supabase/gotrue:v2.196.0` | вход, регистрация, письма, JWT | 20 МиБ |
| PostgREST | `postgrest/postgrest:v14.17` | таблицы по правилам RLS | 37 МиБ |
| Caddy | `caddy:2.11.7-alpine` | HTTPS, маршруты, проверка `apikey`, CORS | 45 МиБ |

\* Замер в GitHub Actions, прогон с обычными лимитами (раздел 4).

Версии GoTrue и PostgREST взяты те же, что в официальной сборке Supabase
для своего сервера (`supabase/docker/docker-compose.yml`, ветка master на
12.10.2026).

**Как Caddy заменяет шлюз Supabase.** У Supabase запросы принимает Kong,
а с 2026 года Envoy. Caddy делает ровно ту часть, которой пользуется
`supabase-js`:

- `/auth/v1/*` ведёт в GoTrue, `/rest/v1/*` — в PostgREST;
- заголовок `apikey` обязателен и должен быть ключом `anon` или
  `service_role`, иначе ответ 401 с тем же текстом, что у Supabase;
- без ключа открыт только `/auth/v1/verify`: по этой ссылке человек
  переходит из письма, токен в ней одноразовый, его проверяет GoTrue;
- CORS разрешён только адресам сайта, чужой сайт получает 403;
- описание схемы (OpenAPI) выключено, тело запроса не больше 1 МБ.

**Настройки под маленький сервер.**

- PostgreSQL: `shared_buffers` 128 МБ, `max_connections` 30,
  `work_mem` 2 МБ, параллельные запросы выключены.
- GoTrue и PostgREST держат по 5 подключений к базе.
- Каждому контейнеру задан лимит памяти, журналы ограничены
  (3 файла по 10 МБ).

**Список приглашённых.** Облачный хук регистрации берёт адреса из
Supabase Vault. В чистом PostgreSQL расширения Vault нет, поэтому
`db/10-vault-shim.sql` делает витрину `vault.decrypted_secrets` с тем же
именем над обычной таблицей. Благодаря этому хук работает без правок.
Шифрования, как в Vault, нет. На своём сервере это почти ничего не
меняет: ключ Vault лежал бы на том же диске, а порт базы наружу закрыт.

### Чего мы лишаемся

| Компонент Supabase | Что делал | Что вместо него |
|---|---|---|
| Studio | веб-панель: таблицы, пользователи, SQL | DBeaver или `psql` через SSH-туннель; список аккаунтов — SQL-запросом ([docs/SERVER.md](SERVER.md), «Доступ к базе») |
| Kong / Envoy | шлюз | Caddy. Не поддерживается `?apikey=` в адресе: он нужен только Realtime, а сайт им не пользуется |
| Storage | загрузка файлов | пока ничего: сайт файлы не принимает |
| Realtime | живые обновления по WebSocket | не нужен: в коде нет ни одного `channel()` |
| Edge Functions | серверный код | не нужен сейчас; для оплаты понадобится свой серверный код (раздел 7) |
| Analytics (Logflare, Vector) | журналы в панели | `docker compose logs` плюс письма о сбоях (этап 1) |
| Supavisor | пул подключений | не нужен при 10 подключениях |
| postgres-meta, imgproxy | служебные для Studio и картинок | не нужны |
| расширения образа `supabase/postgres` (pg_graphql, pg_net, pg_cron, pgsodium, Vault) | GraphQL, HTTP из базы, задания, шифрование | не используются; ночную копию делает cron на сервере (этап 1) |

Поиск по `app/src` подтверждает: сайт обращается только к `auth.*`,
`from('profiles')`, `from('kits')` и `rpc('delete_own_account')`.
Вызовов `storage`, `channel` и `functions.invoke` нет.

### Как вернуть Storage, когда понадобятся загрузки работ

1. Добавить в compose контейнер `supabase/storage-api` (той же версии,
   что в официальной сборке).
2. Хранить файлы не на диске сервера, а в Yandex Object Storage
   (S3-бэкенд Storage). Тогда диск 40 ГБ не кончится, а у бакета есть
   своя версионность для копий.
3. Создать роль `supabase_storage_admin` (схему `storage` Storage
   заводит сам, как GoTrue заводит `auth`).
4. Добавить в Caddy маршрут `/storage/v1/*` с той же проверкой
   `apikey` и поднять лимит тела запроса до размера работы.
5. Написать правила RLS на `storage.objects`: ученик видит свои файлы,
   репетитор — файлы своих учеников.
6. Замерить память той же пробой. Ориентир — ещё 60–120 МБ, но это
   оценка, не замер. На 2 ГБ места хватает, на 1 ГБ будет тесно.

`imgproxy` (преобразование картинок) для работ не нужен.

| Группа | Проверки (все ✓ в обоих прогонах CI) |
|---|---|

| Второй человек и RLS | Борис: регистрация по списку принята, сессии до подтверждения нет; Борис: пришло письмо «Подтвердите почту — Будет на ЕГЭ» от noreply@budetege.ru; Борис: письмо из шаблона supabase/templates (русский текст, ссылка на /voyti/podtverzhdenie/); RLS: второй человек видит только свой профиль; RLS: чужие коды комплектов не видны; RLS: чужой профиль не меняется; RLS: нельзя записать комплект на чужой аккаунт (42501); RLS: нельзя удалить чужие комплекты; Без входа: профили не видны, записать и удалить нельзя; Профиль Анны после попыток Бориса не изменился |
| Шлюз Caddy | Без apikey и с чужим ключом — 401; Описание схемы (OpenAPI) не отдаётся; Чужой сайт не проходит CORS; Порт базы не отвечает по HTTP (опубликован только на 127.0.0.1) |
| Сброс пароля, токен, удаление | Сброс пароля: письмо «Сброс пароля — Будет на ЕГЭ» со ссылкой на /voyti/novyy-parol/; Ссылка сброса даёт сессию на /voyti/novyy-parol/, новый пароль сохраняется; Старый пароль больше не подходит, новый подходит; Обновление токена (refresh token) работает; Удаление аккаунта: войти больше нельзя, профиль удалён каскадом |
| Нагрузка и память | Нагрузка: 30 входов и 300 чтений разом, ошибок сервера нет (5–6 входов отсекает ограничение частоты); Подбор пароля упирается в ограничение частоты, подделка X-Forwarded-For не помогает; Ни один контейнер не упёрся в лимит памяти (OOMKilled=false, без перезапусков) |

Что нашлось по дороге:

- **Ограничение частоты входа с одного адреса:** 150 запросов за
  5 минут, разом не больше 30. Это защита от подбора пароля, и подделкой
  `X-Forwarded-For` её не обойти: Caddy подставляет настоящий адрес. Но
  у класса за одним школьным IP 30 входов одновременно — уже граница.
  На этапе 1 подниму `GOTRUE_RATE_LIMIT_TOKEN_REFRESH` (например, до
  450). Проверку подбора оставлю.
- **Писем — не больше 30 в час на весь сервис** (`RATE_LIMIT_EMAIL_SENT`).
  Для одного вас этого достаточно. Перед открытием регистрации для
  класса лимит надо поднять и сверить с ограничениями SMTP Яндекс 360
  (этап 1).
- GoTrue не отдаёт пароль SMTP по соединению без шифрования. Для
  Яндекс 360 это не помеха: там SSL на порту 465.

## 4. Память: помещается ли в 1 ГБ

Цифры получены в GitHub Actions, `docker stats` раз в секунду, на
`ubuntu-24.04` ([запуск 38262409584](https://github.com/NVbagaeva/socrat-olymp-/actions/runs/38262409584), оба прогона зелёные):

| Контейнер | Покой | Пик сценария | Буферы базы заполнены | Лимит (обычный / 1 ГБ) |
|---|---|---|---|---|
| db | 32 | 47 | **166–169** | 256 / 192 |
| auth (GoTrue) | 13–15 | 20 | — | 128 / 64 |
| rest (PostgREST) | 7 | 36–37 | — | 96 / 64 |
| caddy | 14 | 43–45 | — | 64 / 48 |
| **итого контейнеров** | **67–68** | **145–149** | **264–271** | 544 / 368 |
| dockerd + containerd + shim (RSS) | | 213–218 | | |

Первое число — прогон с обычными лимитами, второе — с урезанными.
Mailpit (около 19 МиБ) есть только в пробе и в итог не входит.
Нагрузка: 30 одновременных входов, p50 550–740 мс (это bcrypt на
одном ядре машины CI), и 300 одновременных чтений профиля, p50 230–315 мс.

Caddy в урезанном прогоне дошёл до 45 из 48 МиБ. На сервере ему нужен
лимит 64 МиБ.

«Худший случай» — пик сценария, когда буферы базы заполнены целиком.
Для этого таблица больше 128 МБ загружается в `shared_buffers` через
`pg_prewarm`, а потом удаляется. Так база будет выглядеть через год-два,
когда данных станет много.

**Расчёт для сервера «1 ГБ»** (ядро резервирует часть памяти, доступно
около 955–970 МиБ; дальше считаю от 960):

| Что | МиБ | Откуда |
|---|---|---|
| четыре контейнера, худший случай | 264–271 | замер |
| dockerd, containerd, shim | ~210 | замер на машине CI, RSS (213–218 с Mailpit, без него меньше) |
| Ubuntu 24.04 без нагрузки | ~300 | внешний замер на VPS 1 ГБ — около 310 МиБ (не проверено нами), пример `free -m` — 317 МиБ; на сервере проверим `free -m` |
| **итого** | **~780** | |
| запас от 960 МиБ | **~19 %** | требование — не меньше 25 % |
| то же с урезанной Ubuntu (без snapd, multipathd, ModemManager; −70…100 МиБ) | ~26–28 % | на грани |
| **то же на сервере «2 ГБ»** (~1950 МиБ) | **~60 %** | |

Вывод: **набор в 1 ГБ запускается и работает.** Второй прогон CI с
урезанными лимитами (сумма 368 МБ) прошёл весь сценарий без
перезапусков и OOM. Swap 1 ГБ закрывает кратковременные всплески:
обновление пакетов, ночную копию, `docker compose pull`.

**Но запаса в 25 % на 1 ГБ нет:** около 19 % со стандартной Ubuntu и
26–28 % с урезанной. Цифра Ubuntu — внешняя оценка, а не наш замер, так
что запас может оказаться и чуть больше, и меньше. Storage для работ
добавит ещё 60–120 МиБ (оценка), и запаса не останется совсем.

**Нужно 2 ГБ.** Там запас около 60 %, и Storage помещается без
настройки.

Источники цифры по Ubuntu:
[сравнение VPS с замером `free -m`](https://bestusavps.com/best-for/ubuntu/)
(партнёрский сайт хостингов, методика не описана) и
[пример `free -m` на сервере 1 ГБ](https://www.centron.de/en/tutorial/how-to-add-and-configure-swap-memory-on-ubuntu-24-04/).

1. 2 ГБ дают запас около 60 %; на 1 ГБ его около 19 %, это меньше
   требуемых 25 %. Storage для работ потом встанет без пересборки,
   обновления и ночная копия не упираются в swap.
2. Цена в бюджете, IPv4 входит, оплата помесячно, без годовой
   предоплаты.
3. Дата-центры в Москве. Тариф меняется в панели без переустановки, а
   Ubuntu 24.04 есть в списке.
4. Канал 1 Гбит/с с 32 ТБ бесплатно — для API кабинета это с огромным
   запасом.

Чего опасаться: FirstVDS поднимал цены трижды за два года, и на
работающих серверах тоже. Если «Старт» подорожает дальше 700 ₽,
переезжаем по процедуре из раздела 5.

Дешевле — **RUVDS «Старт Хит SSD» на 1 ГБ за 349 ₽** — не советую.
Набор там запустится, но запаса около 19 % вместо 25 %. Как поменять
«Старт» на тариф больше без переустановки, на странице не сказано, и
при росте, скорее всего, придётся переезжать. Экономия — 250 ₽ в месяц.

Второй вариант на 2 ГБ — **VDSina Standard за 600 ₽**. Но там диск
NVMe и смена тарифа без переустановки не подтверждены, а цены в 2023
подняли без предупреждения.

Timeweb Cloud не советую: за 2 ГБ в Москве 2140 ₽, втрое дороже FirstVDS.

## 7. Что дальше и чего этот этап не решает

- **Оплата.** ЮKassa требует серверного кода, который принимает
  уведомления о платежах. В облегчённом наборе его нет. Когда до
  оплаты дойдёт, это будет отдельный небольшой сервис рядом с GoTrue и
  PostgREST, и на 2 ГБ под него хватит места.
- **Регистрация учеников** не открывается до уведомления в
  Роскомнадзор и публикации документов (этап 2). До тех пор список
  приглашённых — только ваш адрес.
- **HTTPS для api.budetege.ru** Caddy получит сам от Let's Encrypt,
  как только появится A-запись (этап 2).

## 8. Чек-лист заказа с телефона

Делать после вашего «да» на рекомендацию. Пароли и IP в чат не
присылайте.

1. Откройте [firstvds.ru → VDS](https://firstvds.ru/products/vds_vps_hosting),
   тариф **«Старт»**, вариант **NVMe**.
2. Выберите:
   - **дата-центр:** Москва (любой из двух);
   - **ОС:** **Ubuntu 24.04**, без панели. От ispmanager откажитесь:
     он не нужен и занимает память;
   - **дополнительные IP:** не нужны;
   - **автобэкап:** можно не включать, копию базы сделаем сами на
     этапе 1. Если хотите второй слой защиты, это около 50 ₽ в месяц
     (1,2 ₽ за ГБ).
3. Оплатите **1 месяц**: скидок за длинный период нет.
4. Придёт письмо с **IP-адресом** и **паролем root**. Не пересылайте его
   и не вставляйте в чат.
5. На GitHub откройте репозиторий → **Settings → Secrets and variables →
   Actions → New repository secret** и создайте два секрета:
   - `SERVER_HOST` — IP-адрес из письма;
   - `SERVER_ROOT_PASSWORD` — пароль root из письма.

   Пароль понадобится один раз — кнопке «Подготовить сервер» на этапе 1.
   Она заведёт пользователя `deploy` со входом только по ключу и
   выключит вход root и вход по паролю. После этого секрет
   `SERVER_ROOT_PASSWORD` можно удалить.
6. Напишите мне «сервер заказан». IP мне знать не нужно: workflow
   возьмёт его из секретов.

Что понадобится позже, не сейчас:

- **Этап 1:** почтовый ящик `noreply@budetege.ru` в Яндекс 360 с паролем
  приложения для SMTP и бакет в Yandex Object Storage для копий. Что
  куда положить — [docs/SERVER.md](SERVER.md).
- **Этап 2:** A-запись `api` → IP сервера в DNS budetege.ru.

## 9. Как повторить пробу

Проба стала проверкой боевого набора: workflow `lite-server.yml` на
машине GitHub проходит весь путь сервера — подготовку, развёртывание по
HTTPS, этот же сценарий с замером памяти, копию и восстановление
([docs/SERVER.md](SERVER.md), «Как это проверяется»). Он запускается сам на
pull request, который меняет `infra/lite/`, `supabase/trial/` или
`supabase/templates/`, и вручную: Actions → Lite server.
