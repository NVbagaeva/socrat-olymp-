# Вход и личный кабинет: пробная версия

Документ для владельца проекта. Описывает, как включить вход на сайте,
что для этого завести вручную, что хранится в базе и что отложено до
регистрации настоящих учеников.

Коротко: сайт остаётся статическим на Timeweb, как сейчас. Вход и база —
в облачном сервисе Supabase (проект в Германии, бесплатный тариф). Сайт
ходит к нему прямо из браузера. Регистрация открыта только для адресов
из списка, который хранится в самом сервисе и в репозиторий не попадает.
Пока флаг входа не включён в настройках GitHub, на сайте ничего не
меняется: ни кнопки «Войти», ни лишнего кода.

## Что получилось

| Где | Что |
|---|---|
| Шапка на компьютере | «Войти» и «Начать бесплатно» (ведёт на регистрацию). После входа — кружок с инициалами, в меню «Мой кабинет» и «Выйти» |
| Шапка на телефоне | «Войти» в меню-бургере; на страницах заданий — на месте колокольчика справа вверху, кнопке «?» и закреплённым панелям не мешает |
| `/voyti/` | Вкладки «Войти» и «Зарегистрироваться». Вход: почта, пароль, «Запомнить меня», «Забыли пароль?». Регистрация: имя, почта, пароль от 8 знаков с подсказкой, две карточки «Я ученик» и «Я репетитор» |
| `/voyti/podtverzhdenie/` | Куда ведёт ссылка из письма подтверждения |
| `/voyti/novyy-parol/` | Куда ведёт ссылка из письма сброса пароля |
| `/kabinet/` | Имя, почта, роль (меняются); «Что уже сохранено»; «Выйти», «Удалить аккаунт» с подтверждением |
| Чужая почта | «Регистрация пока по приглашению.» Список адресов браузер не видит |
| Флаг выключен | Кнопок нет, страницы входа говорят «Вход пока недоступен», SDK в сборку не попадает |

Снимки экранов: `docs/screenshots/auth/` (1440 и 390).

Два честных отступления от задания, оба следствие статического хостинга:

- **Cookie сессии httpOnly нет.** Статический сайт не может поставить
  такую cookie: нет сервера, который бы её выдал. Сессия хранится в
  хранилище браузера (localStorage при «Запомнить меня», иначе
  sessionStorage), с ротацией refresh-токена. Выход отзывает сессию на
  сервере. Сторонних скриптов на сайте нет, поэтому украсть сессию
  скриптом неоткуда. Появится свой сервер (план С-1 в
  `CABINET_UX_SPEC.md`) — cookie станет возможной.
- **Данные лежат в Германии** (регион Frankfurt у Supabase; российского
  региона у сервиса нет). Для одного вашего аккаунта это допустимо, для
  учеников — нет (`LEGAL IP RU.md` §3). См. «Отложено» ниже.

## Что завести вручную — пошагово

Названия кнопок в панели Supabase со временем меняются; если что-то не
сходится, ориентируйтесь на смысл шага. Снимков панели Supabase здесь
нет: из этой сессии в неё попасть нельзя, поэтому каждый шаг описан
словами и указано, где пункт лежит в меню.

Пароли и ключи **в чат не присылаются**. Публичные значения (адрес
проекта и публичный ключ) вписываются в GitHub как переменные, список
адресов — в Vault проекта Supabase.

### Шаг 1. Аккаунт и проект

1. Откройте supabase.com, нажмите **Start your project**. Войдите через
   GitHub (тот же аккаунт, что для репозитория) или по почте.
2. **New project**. Организация — личная (создаётся сама). Поля:
   - Name: `budetege` (любое);
   - Database password: придумайте длинный пароль, сохраните в
     менеджере паролей. Он нужен только для прямого подключения к базе,
     сайту он не нужен;
   - Region: **Frankfurt (eu-central-1)** — ближайший;
   - Plan: **Free**.
3. Подождите две-три минуты, пока проект создаётся.

### Шаг 2. Адрес и публичный ключ

1. Слева внизу **Project Settings** (шестерёнка) → **API Keys** (или
   **Data API**, в зависимости от версии панели).
2. Скопируйте **Project URL** вида `https://abcdefghij.supabase.co`.
3. Скопируйте **публичный** ключ: он называется `anon` `public` или
   `publishable` (начинается с `sb_publishable_` или `eyJ…`). Его можно
   показывать: сам он ничего не открывает, доступ к строкам решают
   правила базы.
4. **Не копируйте** ключ `service_role` / `secret`. Он открывает базу
   целиком, в сайт и в GitHub ему попадать нельзя. Проверка
   `pnpm test:secrets` ловит его в сборке.

### Шаг 3. База: таблицы и правила

1. Слева **SQL Editor** → **New query**.
2. Откройте в репозитории файл
   `supabase/migrations/20261011120000_auth_trial.sql`, скопируйте
   содержимое целиком, вставьте в редактор, нажмите **Run**.
3. Внизу должно появиться «Success. No rows returned». Если ошибка —
   пришлите её текст (в нём нет секретов).

Что создаётся: таблицы `profiles` и `kits`, правила доступа (RLS),
функция удаления аккаунта, функция-хук регистрации по списку.

### Шаг 4. Список разрешённых адресов (Vault)

1. Слева **Project Settings** → **Vault** (раздел Integrations или
   Database, зависит от версии панели).
2. **Add new secret**:
   - Name: `allowed_emails` — ровно так, строчными;
   - Secret: ваш адрес почты. Несколько адресов — через запятую.
3. Сохраните.

Хук регистрации читает этот секрет при каждой попытке регистрации.
Адреса не в списке получают «Регистрация пока по приглашению». Секрета
нет — регистрация закрыта для всех.

### Шаг 5. Включить хук регистрации

1. Слева **Authentication** → **Hooks** (иногда раздел называется
   **Auth Hooks**).
2. Найдите **Before User Created** → **Enable hook** (или **Add hook**).
3. Тип: **Postgres**. Schema: `auth_hooks`. Function:
   `before_user_created`.
4. Сохраните и убедитесь, что переключатель хука включён.

Если такого хука в списке нет, значит у проекта старая версия службы
входа: в **Project Settings → Infrastructure** обновите Auth до
последней версии и повторите.

### Шаг 6. Настройки входа

Слева **Authentication** → **Sign In / Providers** (или **Providers**):

1. **Email** — включён. Внутри:
   - **Confirm email** — включено (письмо подтверждения обязательно);
   - **Secure email change** — включено;
   - **Minimum password length** — `8`;
   - **Password requirements** — без требований к символам (длина
     важнее набора знаков).
2. **Allow new users to sign up** (в разделе **Settings** там же) —
   включено: регистрацию закрывает хук из шага 5, а не этот
   переключатель.
3. **Anonymous sign-ins** — выключено.

Слева **Authentication** → **URL Configuration**:

1. **Site URL**: `https://budetege.ru`.
2. **Redirect URLs** → **Add URL**, две строки:
   - `https://budetege.ru/voyti/podtverzhdenie/`
   - `https://budetege.ru/voyti/novyy-parol/`

Без этих адресов ссылки из писем будут вести на главную, и
подтверждение не сработает.

Слева **Authentication** → **Rate Limits** (защита от перебора; значения
по умолчанию подходят, проверьте):

- Email sent — `2` в час на встроенной почте (с своим SMTP можно больше);
- Sign-ups and sign-ins — `30` за 5 минут с одного IP;
- Token verifications — `30` за 5 минут.

Письмо на один и тот же адрес служба отправляет не чаще раза в минуту
(это отдельная настройка **Email → SMTP → Minimum interval**, по
умолчанию 60 секунд); сайт показывает отсчёт.

### Шаг 7. Письма

1. Слева **Authentication** → **Emails** → **Templates**.
2. Для трёх шаблонов замените тему и текст на содержимое файлов из
   `supabase/templates/` (таблица в `supabase/templates/README.md`):
   **Confirm sign up**, **Reset password**, **Change email address**.
3. Отправитель. На бесплатном тарифе встроенная почта Supabase
   отправляет письма **только на адреса участников проекта** — то есть
   на вашу почту, которой вы вошли в Supabase. Для пробы этого
   достаточно, ничего настраивать не нужно. Если ваш адрес в
   `allowed_emails` другой, добавьте его участником проекта
   (**Organization → Team → Invite**) или настройте свой SMTP.
4. Свой SMTP (понадобится для настоящих пользователей): **Authentication
   → Emails → SMTP Settings** → **Enable Custom SMTP**. У домена уже есть
   Яндекс 360: Host `smtp.yandex.ru`, Port `465`, Username — ящик вида
   `noreply@budetege.ru`, Password — **пароль приложения** из настроек
   Яндекс ID (не пароль от ящика), Sender email — тот же ящик, Sender
   name — «Будет на ЕГЭ». DNS-записи домена (MX, SPF, DKIM) для Яндекса
   уже есть, новых не нужно.

### Шаг 8. Переменные в GitHub

В репозитории **Settings → Secrets and variables → Actions → вкладка
Variables** (именно Variables, не Secrets: значения публичные, и так их
видно в логах сборки) → **New repository variable**, три штуки:

| Название | Значение |
|---|---|
| `NEXT_PUBLIC_AUTH_ENABLED` | `1` |
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL из шага 2 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | публичный ключ из шага 2 |

Чтобы выключить вход, удалите переменную `NEXT_PUBLIC_AUTH_ENABLED` (или
поставьте `0`) и запустите **Actions → Deploy → Run workflow**. Сайт
соберётся без входа.

### Шаг 9. Публикация и проверка

1. Слейте pull request. Публикация соберёт сайт с переменными из шага 8.
2. Откройте budetege.ru: в шапке справа должно быть «Войти».
3. Зарегистрируйтесь своим адресом из `allowed_emails`. Письмо придёт
   на почту (если нет — «Спам»; и см. шаг 7, пункт 3). Ссылка откроет
   «Почта подтверждена», в шапке появится кружок с инициалами.
4. Попробуйте зарегистрировать любой другой адрес: должно быть
   «Регистрация пока по приглашению».
5. В кабинете смените роль и имя, выйдите, войдите снова, попробуйте
   «Забыли пароль?».

### Бесплатный тариф: два ограничения

- **Проект засыпает после недели без обращений.** Разбудить: открыть
  проект в панели и нажать **Restore project** (минута-две). Пока
  проект спит, кнопка «Войти» есть, но вход отвечает «Нет связи с
  сервисом входа». Если это будет мешать, можно добавить в GitHub
  Actions запуск раз в несколько дней, который делает один запрос к
  проекту, — отдельной правкой.
- **Резервных копий нет.** Для пробы с одним аккаунтом терять нечего.
  Для настоящих данных — см. «Отложено».

## Что хранится в базе

Таблицы создаёт SQL из шага 3. Пароли сайт не хранит нигде: их хеширует
служба входа Supabase (bcrypt), в таблицах ниже пароля нет.

| Таблица | Поле | Что это | Откуда берётся |
|---|---|---|---|
| `auth.users` (служебная, Supabase) | `email`, хеш пароля, даты подтверждения и входа, `user_metadata` (имя, роль) | Аккаунт | Регистрация, правка профиля |
| `profiles` | `id` | Тот же, что у аккаунта | Триггер при создании аккаунта |
| | `name` | Имя, до 80 знаков | Регистрация, кабинет |
| | `role` | `student` или `tutor` | Регистрация, кабинет |
| | `welcome_seen_at` | Когда окно «Впервые здесь?» было отмечено просмотренным | Из браузера при первом входе, если онбординг (PR #129) уже записал это в localStorage |
| | `tour_id`, `tour_done` | Какой тур начинали и пройден ли | Оттуда же |
| | `created_at`, `updated_at` | Даты | Автоматически |
| `kits` | `user_id`, `code` | Код комплекта вида `7K3F-2B` | Репетитор скачал лист из генератора, будучи вошедшим |
| | `scope`, `section` | Номер задания и раздел («№8 · Вычисления…») | Оттуда же |
| | `student_href`, `teacher_href` | Адреса листов (по ним комплект восстанавливается) | Оттуда же |
| | `created_at` | Когда скачан | Автоматически |
| Vault | `allowed_emails` | Список адресов для регистрации | Вручную, шаг 4 |

Чего в базе **нет** намеренно: прогресса тренажёра, сессий тренировок,
прочитанной теории, «Моих комплектов» целиком. Всё это живёт в браузере,
как и раньше, и вход на него не влияет. Кабинет показывает только то,
что действительно лежит в таблицах.

Удаление аккаунта (кнопка в кабинете, с подтверждением) удаляет строку в
`auth.users`; профиль и комплекты удаляются каскадом. Данные в браузере
остаются.

## Как это устроено в коде

| Что | Где |
|---|---|
| Настройки и флаг | `app/src/lib/auth/config.ts` |
| Чтение сессии без SDK (для шапки) | `app/src/lib/auth/session.ts` |
| Клиент Supabase, грузится по требованию | `app/src/lib/auth/client.ts` |
| Ошибки по-русски | `app/src/lib/auth/errors.ts` |
| Профиль, перенос фактов онбординга, удаление | `app/src/lib/auth/profile.ts` |
| Коды комплектов в аккаунт | `app/src/lib/auth/kits.ts`, точка в `lib/komplekt.ts` (`onKitRemembered`) |
| Блок в шапке | `app/src/components/auth/AuthWidget.tsx` |
| Экраны | `app/src/components/auth/*Screen.tsx`, страницы в `app/src/app/voyti/`, `app/src/app/kabinet/` |
| Тексты | `app/src/content/auth.ts`, `auth-ui.ts` |
| База, хук, письма | `supabase/` |
| Проверка в браузере с моком службы | `app/scripts/check-auth.mjs`, `pnpm test:auth`, `pnpm test:auth-disabled` |
| CI | `.github/workflows/auth.yml` (сборка со входом), шаг в `check.yml` (сборка без входа), переменные в `deploy.yml` |

SDK входа (около 45 КБ) не входит в первую загрузку ни одной страницы:
шапка читает сессию из хранилища сама, SDK подтягивается на страницах
входа и кабинета, при нажатии «Выйти» и при записи комплекта. Бюджет
`pnpm test:first-load` не менялся.

Защита от перебора: лимиты службы входа (шаг 6), письмо не чаще раза в
минуту с отсчётом на экране. Пароль от 8 знаков проверяется и на сайте,
и в службе.

## Отложено до настоящей регистрации учеников

Для пробы с одним вашим аккаунтом это не блокер. Перед тем как пускать
учеников, нужно:

1. **Согласие на обработку персональных данных** — отдельный экран с
   версией и датой (`CABINET_UX_SPEC.md`, экран У-2), тексты от
   юриста. Для младше 14 лет — согласие родителя.
2. **Политика конфиденциальности** — опубликовать, ссылка «Обработка
   данных» в подвале сейчас ведёт в никуда.
3. **Уведомление в Роскомнадзор** об обработке персональных данных — до
   первой регистрации (`LEGAL IP RU.md` §3).
4. **Хранение данных в России.** Supabase Cloud для данных учеников не
   подходит. Путь — план С-1: свой сервер в РФ с Supabase на нём. Код
   сайта при переезде не меняется: тот же SDK, тот же API, меняются
   три переменные из шага 8; данные переносятся `pg_dump`.
5. **Резервные копии** — ежедневный зашифрованный дамп в Yandex Object
   Storage (как в С-1), проверка восстановления.
6. **Свой SMTP** российского провайдера (Яндекс 360 уже есть, шаг 7,
   пункт 4) вместо встроенной почты, которая пишет только участникам
   проекта.
7. **Cookie httpOnly** для сессии — только со своим сервером.
8. **Открыть регистрацию**: заменить хук со списком на регистрацию по
   коду класса или приглашению учителя (С-4).
9. **Что переносить в аккаунт** из браузера (прогресс, комплекты
   целиком) — отдельное решение, экран У-4.
