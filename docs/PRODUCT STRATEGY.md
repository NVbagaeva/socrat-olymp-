## 1. Краткий вывод CTO

1. **Остановиться и сменить архитектуру нужно сейчас** — не потому, что страница №3 плохая, а потому что у тебя одна страница, а не тридцать. Это самый дешёвый момент.
2. **Рекомендуемый путь — вариант В с быстрым переходом в Б**: существующий HTML становится *эталонным прототипом* и источником контента (56 прототипов, SVG, подсказки, логика проверки), а не фундаментом кода. В течение 3–4 недель его функциональность переезжает в Next.js-приложение; сам HTML остаётся как reference и demo.
3. **Одно изменение в утверждённой архитектуре:** продакшен-инфраструктура — **в России** (ПДн россиян по 152-ФЗ + нестабильность Vercel/Netlify из РФ в 2026). Стек кода не меняется: Supabase разворачивается self-hosted в Docker на российском VDS, Next.js — там же. Supabase Cloud (EU) остаётся только для dev/staging с тестовыми данными.
4. **Защита продукта** — не в сокрытии HTML, а в том, что у клиента нет ничего ценного: ни базы задач, ни ответов, ни генераторов, ни проверки. Клиент получает по одной задаче и отправляет ответ на сервер. Скопировать интерфейс можно, скопировать продукт — нет.
5. **MVP = «репетитор + его ученики + №3»**. Не строить B2C-подписку и оплату до того, как 5–10 репетиторов реально пользуются бесплатно.

## 2. Что у тебя сейчас

- `dz_stereometria.html` — 56 прототипов №3, SVG-чертежи, подсказки, проверка ответа в браузере, отчёт учителю.

## 3. Главная архитектурная ошибка, которую нельзя допустить

**Продолжать делать HTML-страницы «по номерам» и надеяться склеить их потом.**

Почему это тупик:
- В каждой странице задачи, ответы и проверка живут вместе → ни защиты, ни статистики, ни учителя без переписывания.
- 30 страниц = 30 разных копий одной и той же логики (ввод, проверка, подсказки), которые начнут расходиться.
- Пользователи, группы, прогресс невозможны без сервера — их не «добавить потом», под них проектируется база.

Вторая ошибка — противоположная: **уйти в идеальную платформу на год без пользователей**. Отсюда жёсткий MVP ниже.

## 4. Рекомендуемая архитектура (обновление)

Архитектура из TECH_ARCHITECTURE.md сохраняется полностью, кроме размещения:

```
Ученик / Учитель (браузер, телефон)
        │ HTTPS  (домен .ru, SSL, российский CDN не обязателен на старте)
        ▼
┌────────────────────────────────────────────────────────────────┐
│  Российский VDS/облако (Timeweb Cloud / Selectel / Yandex Cloud) │
│  Docker Compose:                                                 │
│   • next-app (Next.js 15, Node 22)                               │
│   • supabase self-hosted: postgres 16, gotrue(auth), storage,    │
│     kong, realtime (postgrest/studio — только на staging)        │
│   • redis (rate limit, кэш)                                      │
│   • caddy/traefik (SSL, reverse proxy)                           │
│  Бэкапы: wal-g/pg_dump → Yandex Object Storage / Timeweb S3      │
└────────────────────────────────────────────────────────────────┘
        │
   ЮKassa (платежи, чеки)   Sentry (без ПДн)   PostHog EU / Яндекс Метрика
```

**Почему так → альтернативы → почему нет:**
- *Self-hosted Supabase* сохраняет RLS, Auth, Storage и весь написанный под них код. Альтернатива — managed Postgres (Yandex Cloud) + Auth.js: дешевле в обслуживании, но заново писать auth/storage/RLS-контекст (+2–3 недели). Оставляем как план Б, если self-hosted окажется тяжёлым.
- *VDS с Docker* вместо PaaS: Timeweb App Platform умеет деплоить Next.js, но не весь стек Supabase. VDS 4 vCPU / 8 GB (~1500–2500 ₽/мес) тянет всё до нескольких тысяч учеников.
- *Vercel + Supabase Cloud EU* — идеально для DX, но недоступно/нестабильно для российских пользователей и не проходит по локализации ПДн. Используем только как dev/staging.

Ориентировочная стоимость продакшена: **2 000–4 000 ₽/мес** (VDS + S3 + домен) до ~5 000 учеников.

## 5. Frontend

- **Next.js 15 + React 19 + TypeScript.** Next.js нужен: серверный рендер (ответы не на клиенте), Server Actions, роутинг по ролям, SEO для лендинга. Vue/SvelteKit — не хуже технически, но Claude Code и экосистема (shadcn, react-pdf, r3f) сильнее у React.
- **TypeScript**, не JS: типы из БД → API → UI ловят ошибки до продакшена; Claude Code с типами делает меньше ошибок.
- Организация компонентов: `components/ui` (примитивы) → `components/math`, `components/figures` (доменные) → `features/*/components` (экранные). См. REPOSITORY_STRUCTURE.md.
- Существующие SVG и стили страницы №3 переезжают почти как есть (см. §19).

## 6. Backend

- **Node.js внутри Next.js** (Server Actions + Route Handlers). Отдельный сервис (NestJS/FastAPI) не нужен до B2B-интеграций. Python не нужен: генерация задач — арифметика, не ML.
- **Не REST и не GraphQL** для внутреннего UI — типизированные Server Actions. Публичный REST v1 появится под B2B.
- Бизнес-логика — в `src/features/*/service.ts` и `src/tasks`, никогда в компонентах.

## 7. Database

PostgreSQL 16, схема — DATABASE_SCHEMA.md. Ключевое отличие от твоей модели «Task с полями answer/solution»:

| Ты предложила | Профессиональная структура | Зачем |
|---|---|---|
| Task = условие + ответ + решение в одной строке | `prototypes` → `task_templates` → `generated_tasks` + отдельная `answers` | Ответ физически отделён от задания (защита); один прототип — тысячи заданий; статистика по прототипу |
| Figure как поле | `figure_spec jsonb` + кэш SVG в Storage | Чертёж генерируется из параметров, а не хранится вручную для каждой задачи |
| Topic/Subtopic | `topics` (номер ЕГЭ) → `prototypes` (подтип) + `tags` | Фильтр «призма/пирамида» — это тег/skill, а не отдельный уровень иерархии |
| Homework / Assignment / Result / Progress | `assignments` + `assignment_tasks` + `deadlines`; `attempts` (факты) + `statistics` (агрегат) | Результат не хранится — вычисляется из попыток; агрегат кэшируется |
| Subscription / Tariff / Payment / Access | `plans`, `subscriptions`, `payments`, `entitlements` (§15) | Доступ выдаётся по entitlement, а не по флагу «оплачено» |

Твои 56 прототипов из HTML: **сначала** заводятся как `prototypes` + «статические» шаблоны (параметры зафиксированы, генератор возвращает те же числа), **потом** постепенно параметризуются. Так ничего не теряется в первый день.

## 8. API — пример «ЕГЭ → №3 → Стереометрия → Призма»

1. Ученик открывает `/practice/3/prism`. Middleware проверяет cookie-сессию → роль `student` → пускает.
2. Server Component вызывает `getNextTask({ topic: 3, tags: ['prism'] })`.
3. Guard `requireUser()` подтверждает сессию; `entitlements` проверяют, что №3 доступен ученику (Free или по подписке учителя).
4. Task Engine выбирает шаблон, генерирует задание с seed (или берёт из пула), пишет `generated_tasks` + `answers` (service role).
5. В ответ клиенту уходит `generated_tasks_public`: текст, SVG, id. **Ни seed, ни параметров, ни ответа.**
6. React рендерит условие (KaTeX) и чертёж.
7. Ученик вводит ответ → Server Action `submitAnswer(taskId, '45')`.
8. Сервер: rate limit → загружает `answers.value` service role → `checkAnswer` → пишет `attempts` (`is_correct`, `attempt_no`, время) → классифицирует ошибку → триггер обновляет `statistics`.
9. Клиенту возвращается `{ correct: true }` (или `{ correct: false, attemptsLeft: 2 }`), и по политике — разбор.
10. Дашборд читает `statistics` + `mv_*`.

В сети видно только: `POST /practice/... action=submitAnswer body={taskId, answer}` → `{correct}`. Массового выгруза нет: одна задача за запрос, лимиты, задания привязаны к ученику.

## 9. Authentication

Старт: **email + пароль** и **magic link**. Следующие: **VK ID**, **Яндекс ID**, **Telegram Login** (для родителей/учеников — удобно, отдельный виджет). Google/Apple — не в приоритете для РФ. Реализация — Supabase Auth (GoTrue) self-hosted, OIDC-провайдеры настраиваются конфигом. Ученик регистрируется по коду группы репетитора; самостоятельная регистрация — после MVP.

## 10. Защита контента

Что защищаем и как — по пунктам брифа:

| # | Вопрос | Ответ |
|---|---|---|
| 1 | Что возможно защитить на frontend | Ничего секретного. Можно только затруднить: минификация, отсутствие source maps в проде, разбиение на чанки. Это косметика. |
| 2 | Что невозможно | Любой HTML/CSS/JS, отданный браузеру, можно прочитать и сохранить. Дизайн и вёрстку скопируют, если захотят. |
| 3 | Только на сервере | Банк задач, шаблоны-генераторы, правильные ответы, проверка, классификация ошибок, статистика, PDF, права доступа. |
| 4 | В базе данных | Всё из п.3 + пользователи, группы, попытки, подписки. Ни один файл с задачами не лежит в `public/`. |
| 5 | Чтобы массив не отдавался целиком | Клиент получает ровно одно задание на запрос (или N ≤ 20 для назначения), только свои, по RLS. Нет эндпоинта «список всех задач». |
| 6–7 | API и ограничение доступа | Server Actions с Zod + guard + RLS; лимиты на генерацию (300/сутки ученик); прямой вызов без cookie-сессии → 401. |
| 8 | Auth/authz | Три слоя: middleware → guard в action → RLS. SECURITY.md §2–5. |
| 9 | Premium-контент | `entitlements`: серверная проверка перед выдачей каждого задания/PDF; никаких «спрятанных» вкладок на клиенте. |
| 10 | Алгоритмы проверки | `checkAnswer`, нормализация, дистракторы — только в `src/tasks` (server-only), в бандл не попадают (CI-проверка). |
| 11 | Ответы на сервере | Да, таблица `answers`, RLS запрещает чтение ученику и учителю. |
| 12 | Вся база одним запросом | Невозможно: нет такого действия; RLS отдаёт только принадлежащие пользователю задания; view без seed/params. |
| 13 | Массовый scraping | Лимиты + задания уникальны на ученика (seed) → выкачанное одним не совпадает с другим; водяной знак учителя в PDF; аудит аномальной скорости. |
| 14 | Rate limiting | SECURITY.md §7. |
| 15 | Логи подозрительного | `audit_log` + алерты: >60 ответов/мин, >300 генераций/день, 401/403 всплески, смена IP-страны в сессии. |
| 16 | Обход авторизации | Cookie HttpOnly+Secure, ротация refresh, инвалидация при смене роли, отсутствие «скрытых» клиентских флагов роли. |
| 17 | Прямые запросы к API | Всё требует сессии; CSRF-защита Server Actions; anti-automation на регистрации (Yandex SmartCaptcha). |
| 18 | Админка | Отдельный хост `admin.`, роль `admin` в JWT, 2FA (TOTP) обязательна, IP-allowlist по желанию, аудит всех действий. |
| 19 | Изображения/чертежи | Генерируются из `figure_spec`; исходники сцен — в БД. Публичный SVG — это «картинка», по ней не восстановить генератор. Возможен лёгкий водяной знак/название бренда в углу. |
| 20 | PDF/решения/методички | Только в приватном bucket, signed URL на 1 час, персональный водяной знак (имя учителя, дата, QR) на каждой странице, лог скачиваний. |

**Простыми словами:** представь, что сайт — это касса кинотеатра, а фильм показывают в зале. Скопировать можно вывеску и кассу, но не фильм. Мы делаем так, чтобы «фильм» (задачи, ответы, генераторы, проверка) никогда не выходил за пределы сервера, а зритель получал по одному кадру и только свой.

## 11. Защита кода

- Серверный код никуда не отдаётся — это 80 % ценности.
- Клиентский бандл: без source maps, минификация (Next.js по умолчанию). Обфускаторы не ставим — ломают отладку, дают ноль защиты.
- Репозиторий приватный (GitHub private), 2FA, ветка `main` защищена, секреты только в env.
- Юридически — регистрация ПО в Роспатенте (LEGAL_IP_RU.md §3).

## 12. Admin / CMS

В том же приложении (`app/(admin)`), без внешней CMS. Экраны:
- **Прототипы**: список по темам, статус draft/published/archived, теги, сложность, вес.
- **Шаблоны**: форма с параметрами (name, min, max, step), текст условия с `{{r}}`, formula ответа (для статических — фиксированное число), constraints, дистракторы, загрузка/выбор чертежа (FigureSpec-редактор простой: выбор тела + подписи), кнопка **«Сгенерировать 20 и проверить»** — показывает 20 заданий с ответами и красные флаги (нецелые ответы, нарушенные constraints).
- **Ошибки (error_types)**: справочник типовых ошибок по прототипу.
- **Пользователи/учителя/организации**: роли, статусы, подтверждение учителей.
- **Тарифы/подписки/промокоды**: см. §15.
- **Импорт/экспорт**: JSON банка (для git-версионирования контента).

Правило: **добавление задачи = запись в БД через админку, без деплоя**. Деплой нужен только для новых типов генераторов с нетривиальной формулой (пока нет безопасного DSL).

## 14. Teacher — кабинет и логика ДЗ

**Сценарий:** учитель → «Группы» → группа 11А → «Новое задание» → выбирает №3 → теги «призма» → 10 задач → режим «тренировка/контроль» → дедлайн → «Персональные варианты: да» → «Назначить».

**Backend:** `createAssignment()` создаёт `assignments`, для каждого ученика генерирует 10 `generated_tasks` (seed = hash(assignmentId, studentId, i)) → `assignment_tasks`, `deadlines`. Ученики видят задание мгновенно (Realtime не обязателен — polling при открытии).

**Учитель видит таблицу:** ученик × статус (не начал / в процессе / выполнено) × % верно × время × число попыток × «слабые прототипы» (по `statistics.mastery < 0.6`). Клик по ученику → каждая задача, его ответы, тип ошибки. Кнопки: «Переназначить с новыми числами» (новый seed), «Продлить дедлайн», «Скачать PDF варианта».

**Обратная связь от учителя** (ты выбрала): комментарий к попытке (`attempt_comments`) + отметка «разобрано». Это не образовательная услуга платформы — это инструмент учителя (важно для лицензирования, см. LEGAL).

## 15. Payments и монетизация

### Модели
| Модель | Кто платит | Оценка |
|---|---|---|
| **B2B2C — репетитор/учитель** | Учитель покупает «место для N учеников на год» | **Основная.** Один платёж = 10–30 учеников, низкий CAC, репетитор сам приводит учеников. |
| B2C — ученик | Ученик/родитель | После MVP. Нужен маркетинг, высокая поддержка, чек ниже. |
| Школы | Организация | Год 2. Требует ИП/ООО (юрлица не могут платить самозанятому через ЮKassa) и документов. |

### Тарифы (гипотеза для проверки, не финал)
- **Free (репетитор):** 1 группа, до 5 учеников, только №3, без PDF.
- **Репетитор:** ~2 990 ₽/год за до 15 учеников; **+990 ₽** за каждые +10 мест. Все темы, PDF, статистика.
- **Ученик самостоятельный (позже):** ~490 ₽/мес или 2 990 ₽/год.
- **Trial:** 14 дней полного тарифа для учителя без карты.
- **Seat** = активный ученик в группах учителя (ученик в двух группах одного учителя = 1 seat). Архивирование ученика освобождает seat через 30 дней (защита от «перекручивания»).

### Архитектура
Таблицы: `plans` (код, цена, лимиты jsonb, период), `subscriptions` (owner profile/organization, plan, status, current_period_end, seats, auto_renew), `payments` (provider, provider_id, amount, status, receipt_url), `entitlements` (кому, что, до какого числа — материализованный доступ), `promo_codes`, `promo_redemptions`.

Поток: учитель нажимает «Оплатить» → сервер создаёт `payments(pending)` + платёж в ЮKassa (сумма, описание, чек) → редирект на ЮKassa → webhook `payment.succeeded` (проверяется IP/подпись, идемпотентен) → `payments(succeeded)`, `subscriptions(active)`, пересчёт `entitlements` → письмо. Чек для самозанятой — формируется в «Мой налог» (ЮKassa может передавать данные, но обязанность выдать чек — на тебе; для ИП — автоматизируется полностью).

Прекращение доступа: `pg_cron` ежедневно переводит истёкшие `subscriptions` в `expired` и снимает `entitlements`; данные не удаляются, ученики переходят в режим «только чтение своей статистики», учитель видит баннер «продлить». Grace-период 7 дней.

Проверка доступа **всегда на сервере** в `requireEntitlement('topic:3')` перед выдачей задания/PDF.

## 19. Migration existing HTML

**Можно ли превратить страницу в React без потери?** Да, с оговорками:
- **Переезжает почти без изменений:** SVG-чертежи (в JSX или как файлы), CSS (в Tailwind/CSS-modules — визуал 1:1), тексты условий, подсказки, структура прототипов.
- **Переписывается:** логика проверки (уходит на сервер), хранение задач (в БД), состояние интерфейса (jQuery/vanilla → React state), «отчёт учителю» (становится настоящей статистикой).
- **Не переносится как есть:** inline `<script>` с массивом задач — он и есть то, что нужно убрать.

Точный разбор «что оставить / что вынести» сделаю по файлу, когда он будет в этом чате.

## 22. Tech stack — МОЯ РЕКОМЕНДАЦИЯ

**Frontend:** Next.js 15 + React 19 + TypeScript, Tailwind 4 + shadcn/ui, KaTeX.
**Backend:** Server Actions / Route Handlers в Next.js; Task Engine и Geometry Engine — чистый TS.
**Database:** PostgreSQL 16 (self-hosted Supabase) + RLS, Drizzle ORM, миграции SQL.
**Auth:** Supabase Auth (GoTrue) — email/пароль, magic link; далее VK ID, Яндекс ID, Telegram.
**Storage:** Supabase Storage (self-hosted, S3-совместимый) → бэкап/CDN на Yandex Object Storage.
**Hosting:** российский VDS (Timeweb Cloud или Selectel), Docker Compose, Caddy. Dev/staging — Supabase Cloud EU + локальный Docker.
**Payments:** ЮKassa (карты, СБП), webhooks; чеки — «Мой налог» (самозанятость) → автоматическая касса ЮKassa при ИП.
**Analytics:** Postgres-витрины для учебной аналитики; PostHog EU (без ПДн) или Яндекс Метрика для продуктовой.
**Monitoring:** Sentry, pino-логи → файл/Loki на VDS, Uptime-мониторинг (UptimeRobot/Яндекс Монитор), Telegram-алерты.

**Почему оптимально:** один язык (TS) и одно приложение; безопасность встроена в БД (RLS); всё запускается на одном VDS за ~2–3 тыс ₽/мес; код не привязан к хостингу (Docker), можно переехать на любой российский или зарубежный облак за день; Claude Code знает этот стек лучше всего; масштабируется до десятков тысяч пользователей вертикально (больший VDS + managed Postgres), без переписывания.
