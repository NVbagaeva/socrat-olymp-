# Сервер api.budetege.ru: инструкция владельца

Сервер входа и личных кабинетов: FirstVDS «Старт» NVMe в Москве
(почему он — [docs/hosting-lite.md](hosting-lite.md)). На нём облегчённый
набор Supabase — PostgreSQL, GoTrue, PostgREST и Caddy — из
`infra/lite/`. Сам сайт остаётся статическим на Timeweb.

Всё делается кнопками GitHub Actions, с телефона. На сервер заходить
не нужно, пароли и ключи никуда копировать не нужно.

## Кнопки

Вкладка **Actions** репозитория, слева — workflow, справа — **Run workflow**.

| Кнопка | Что делает | Когда нажимать |
|---|---|---|
| **Сервер: подготовить** | защита сервера, Docker, вход только по ключу | один раз на новом сервере |
| **Сервер: развернуть** | набор на сервер, запуск контейнеров | после подготовки; после изменений в `infra/lite/` или шаблонах писем |
| **Сервер: миграции** | новые таблицы в базе, каталог банка, список приглашённых, редакция правовых документов, администратор, пароль для туннеля | после первого «Развернуть»; когда меняете `ALLOWED_EMAILS`, `ADMIN_EMAIL` или дату редакции документов |
| **Сервер: ключ для сайта** | записывает адрес сервера и его публичный ключ в Variables сайта | один раз после первого «Развернуть»; после переезда на другой сервер |
| **Сервер: тестовые данные** | «Тестовый класс» и тестовые ученики на ваших адресах; режим «удалить» убирает их | в пробном режиме, после того как вы зарегистрировались как репетитор |
| **Сервер: проверить здоровье** | контейнеры, API, сертификат, диск, память, копии, записи почты в DNS (SPF, DKIM, DMARC) | само каждые 30 минут; кнопкой — когда сомневаетесь |
| **Сервер: копия сейчас** | внеочередная копия базы | перед рискованными изменениями |
| **Сервер: проверить восстановление** | копия восстанавливается в пустую базу и сверяется | само каждый понедельник; режим «на сервер» — только при беде |
| **Сервер: обновить** | все пакеты Ubuntu и образы набора | раз в месяц или по письму о проблеме |

Кнопки появляются во вкладке Actions, только когда их файлы есть в
ветке `main`. Поэтому сначала сливаются PR этапа 1, потом — нажатия.

Что происходит само, без кнопок:

- **каждую ночь в 03:30 по Москве** — копия базы в Yandex Object Storage:
  14 ежедневных, 8 еженедельных;
- **каждые 15 минут** — сервер проверяет себя и пишет вам о проблемах;
- **каждые 30 минут** — GitHub проверяет сервер снаружи. Эта проверка
  ловит то, о чём сервер сам написать не может: выключен или недоступен;
- **каждый понедельник** — копия восстанавливается в пустую базу на
  машине GitHub и сверяется по числу строк;
- **каждую ночь** — обновления безопасности Ubuntu, без перезагрузки.

## Первый запуск

### 1. Сервер

Закажите FirstVDS «Старт» NVMe, Ubuntu 24.04, Москва, без панели
([docs/hosting-lite.md](hosting-lite.md), раздел 8). Из письма провайдера
нужны IP-адрес и пароль root.

**Без панели — значит без ispmanager и без «рецептов».** Панель держит
порты 80 и 443, которые нужны набору. Если сервер уже с панелью,
«Развернуть» остановится на строке «Порты 80 и 443 заняты, на сервере
стоит панель ispmanager». Тогда в личном кабинете FirstVDS: **Товары →
Виртуальные серверы**, отметьте сервер галочкой → **Переустановка ОС** →
Ubuntu 24.04, без предустановленного ПО. Дальше — как после
переустановки: удалите секреты `SERVER_KNOWN_HOSTS` и `SERVER_SSH_KEY`
и начните с «Подготовить». Отдельный веб-сервер из образа (apache2,
nginx без панели) «Развернуть» выключает сама и пишет об этом в журнале.

### 2. Почта для писем (Яндекс 360)

С этого ящика уходят письма «Подтвердите почту» и «Сброс пароля». С него
же сервер пишет вам о проблемах. По умолчанию это `noreply@budetege.ru`;
можно взять любой другой ящик домена — тогда впишите его в Variable
`SMTP_USER`.

1. Подключите домен budetege.ru к Яндекс 360 для бизнеса. Нужен ли
   отдельный ящик `noreply@`, решаете вы: в Яндекс 360 каждый ящик
   оплачивается по тарифу.
2. Яндекс 360 попросит добавить в DNS домена записи MX, SPF (TXT) и DKIM
   (TXT). **Записи MX направят всю почту домена в Яндекс:** если у
   budetege.ru уже есть почта в другом месте, сначала решите, где ей жить.
   Без SPF и DKIM письма будут уходить в спам.
3. **Войдите именно в тот ящик, с которого пойдут письма** (проверьте
   адрес на аватарке справа вверху). В нём:
   - Почта → настройки → **Почтовые программы**: включите IMAP и
     «Пароли приложений и OAuth-токены»;
   - Яндекс ID → Безопасность → **Пароли приложений** → Почта: создайте
     пароль. Он (а не основной пароль ящика) пойдёт в секрет
     `SMTP_PASSWORD`.

Пароль приложения, созданный в другом ящике, Яндекс не примет: в журнале
будет «Ответ почтового сервера: 535 … Invalid user or password».

Проверить пароль до GitHub можно с компьютера (macOS: Терминал). Сначала
команда, которая спросит пароль и не покажет его на экране:

```bash
printf 'Пароль приложения: '; stty -echo; read P; stty echo; echo
```

Потом пробное письмо самому себе — `ЯЩИК` везде замените на адрес из
`SMTP_USER`:

```bash
printf 'From: ЯЩИК\r\nTo: ЯЩИК\r\nSubject: test\r\n\r\ntest\r\n' | curl -sS -v --url smtps://smtp.yandex.ru:465 --user "ЯЩИК:$P" --mail-from ЯЩИК --mail-rcpt ЯЩИК -T - 2>&1 | grep -E '^< (235|[45][0-9][0-9])|^curl:'
```

`235 … Authentication successful` — пароль верный; `535 … Invalid user or
password` — пароль из другого ящика; `535 … does not have access rights`
— не включены почтовые программы. В выводе пароля нет. В конце —
`unset P`.

### 3. Хранилище копий (Yandex Object Storage)

1. В [консоли Yandex Cloud](https://console.yandex.cloud) создайте
   платёжный аккаунт и каталог (folder).
2. **Object Storage → Создать бакет:**
   - имя — например, `budetege-backups`;
   - доступ — **ограниченный** (на чтение, к списку и к настройкам);
   - класс — стандартный.
3. **Сервисные аккаунты → Создать:** имя `budetege-backup`, роль
   `storage.editor`.
4. В сервисном аккаунте нажмите **Создать новый ключ → Создать статический
   ключ доступа**. Идентификатор и секрет показываются один раз: сразу
   вставьте их в секреты `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY`.

Копия базы — десятки килобайт, пока аккаунтов немного. Хранение стоит
копейки в месяц.

### 4. Токен GitHub для секретов

«Подготовить сервер» создаёт ключи — вход на сервер и шифрование
копий — и должна сохранить их в Secrets. Для этого нужен токен с правом
записывать секреты, и только его:

GitHub → **Settings** (вашего профиля) → **Developer settings** →
**Personal access tokens** → **Fine-grained tokens** → **Generate new
token**:

- **Expiration:** 7 дней — он нужен только на время первого запуска;
- **Repository access:** Only select repositories → `socrat-olymp-`;
- **Permissions → Repository → Secrets:** Read and write;
- **Permissions → Repository → Variables:** Read and write. Больше ничего.

Скопируйте токен в секрет `GH_SECRETS_TOKEN`. Он нужен двум кнопкам:
«Подготовить» (сохраняет созданные ключи в Secrets) и «Ключ для сайта»
(записывает адрес и публичный ключ в Variables). После них токен можно
удалить и там, и в настройках профиля.

### 5. Secrets и Variables

Репозиторий → **Settings → Secrets and variables → Actions**. Значения
секретов GitHub никому не показывает, даже вам. Variables видны всем, у
кого есть доступ к настройкам репозитория.

**Secrets — вписываете вы:**

| Имя | Что это |
|---|---|
| `SERVER_HOST` | IP-адрес сервера из письма FirstVDS |
| `SERVER_ROOT_PASSWORD` | пароль root из того же письма; после подготовки можно удалить |
| `GH_SECRETS_TOKEN` | токен из шага 4; после подготовки можно удалить |
| `ALERT_EMAIL` | ваша почта для писем о проблемах (и для Let's Encrypt) |
| `SMTP_PASSWORD` | пароль приложения того ящика, что в `SMTP_USER` (шаг 2) |
| `S3_ACCESS_KEY_ID` | идентификатор статического ключа (шаг 3) |
| `S3_SECRET_ACCESS_KEY` | секрет статического ключа (шаг 3) |
| `ALLOWED_EMAILS` | кому открыта регистрация: адреса **через запятую** (пробел, точка с запятой или перенос строки склеят их в один). Пока — ваш адрес и ваши адреса-алиасы для тестовых учеников. «Миграции» пишет в сводке «адресов N» — N должно совпасть |
| `SEED_TUTOR_EMAIL` | почта вашего аккаунта репетитора — для кнопки «Тестовые данные» |
| `SEED_STUDENT_EMAILS` | адреса трёх тестовых учеников через запятую (ваши алиасы); все они должны быть и в `ALLOWED_EMAILS` |
| `ADMIN_EMAIL` | почта аккаунта администратора (необязательно; отдельный адрес-алиас, см. [AUTH.md](AUTH.md)) |
| `DB_ADMIN_PASSWORD` | придумайте пароль для входа в базу через туннель (необязательно) |

**Secrets — создаст «Подготовить сервер» сама:** `SERVER_SSH_KEY`,
`SERVER_KNOWN_HOSTS`, `BACKUP_AGE_IDENTITY`, `BACKUP_AGE_RECIPIENT`. Не
удаляйте их: без `SERVER_SSH_KEY` на сервер не попасть, а без
`BACKUP_AGE_IDENTITY` не расшифровать копии.

**Variables:**

| Имя | Значение |
|---|---|
| `S3_BUCKET` | имя бакета из шага 3, например `budetege-backups` |
| `SMTP_USER` | ящик, с которого уходят письма; по умолчанию `noreply@budetege.ru`. Пароль приложения в `SMTP_PASSWORD` — из этого же ящика |
| `API_DOMAIN` | `api.budetege.ru` (так и по умолчанию) |
| `SITE_ORIGIN` / `SITE_ORIGIN_2` | `https://budetege.ru` / `https://www.budetege.ru` (так и по умолчанию) |
| `ADMIN_SSH_PUBLIC_KEY` | ваш открытый ключ SSH для туннеля к базе (необязательно, см. ниже) |
| `SERVER_READY` | `1` — когда первый запуск прошёл; включает проверки по расписанию |
| `DKIM_SELECTOR` | селектор DKIM для проверки почты, у Яндекс 360 это `mail` (так и по умолчанию) |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | адрес сервера и публичный ключ для сайта — их записывает кнопка «Ключ для сайта», руками не вписывать |
| `NEXT_PUBLIC_AUTH_ENABLED` | `1` — вход на сайте включён ([AUTH.md](AUTH.md)); ставите сами, когда сервер проверен |
| `NEXT_PUBLIC_AUTH_IN_HEADER` | `1` — кнопка «Войти» в шапке; в пробном режиме не ставить |

### 6. Кнопки по порядку

1. **Сервер: подготовить.** В сводке запуска будет «Сервер подготовлен»
   и список созданных секретов. Секреты `SERVER_ROOT_PASSWORD` и
   `GH_SECRETS_TOKEN` теперь можно удалить.
2. **Сервер: развернуть.** В сводке — четыре сервиса, у всех `healthy`.
3. **Сервер: миграции.** В сводке — «Применяю 001-…soglasiya.sql» и
   остальные файлы из `infra/lite/migrations.txt`, «Каталог банка
   обновлён», «Редакция документов: …» и «Список приглашённых обновлён:
   адресов N» — N равно числу адресов в `ALLOWED_EMAILS`. Повторный
   запуск безопасен: применённые миграции не повторяются («Новых
   миграций: 0»), список приглашённых обновляется.
4. **Сервер: ключ для сайта.** В сводке — «`NEXT_PUBLIC_SUPABASE_ANON_KEY` —
   записан, значение скрыто». Секрет `GH_SECRETS_TOKEN` теперь можно удалить.
5. **Сервер: копия сейчас**, потом **Сервер: проверить восстановление**
   (режим «проверка»). В сводке — таблица «записано в копии» и
   «восстановлено», числа совпадают.
6. Variable `SERVER_READY` = `1`.
7. **Сервер: проверить здоровье.** До A-записи будет «A-записи ещё нет,
   проверка пропущена» — это нормально. Строки «почта: SPF на месте» и
   «почта: DKIM на месте» должны быть уже сейчас.

### 7. A-запись и вход на сайте

1. В DNS домена budetege.ru (панель Timeweb) добавьте A-запись: имя
   `api`, значение — IP сервера. Сертификат Caddy получит сам за
   минуту-две после того, как запись разойдётся.
2. **Сервер: проверить здоровье** — «снаружи: https://api.budetege.ru/health
   200, сертификат принят».
3. Variable `NEXT_PUBLIC_AUTH_ENABLED` = `1`, затем **Actions → Deploy →
   Run workflow**. Выкладка сайта идёт около часа; если в это время уже
   идёт другая, новая ждёт её конца. Флаг попадает в сайт при сборке,
   поэтому нужна выкладка, начатая после того, как вы его поставили.
   Страница `https://budetege.ru/voyti/` покажет форму входа. Кнопки
   «Войти» в шапке не будет, пока нет `NEXT_PUBLIC_AUTH_IN_HEADER` = `1`.

### 8. Тестовые данные (пробный режим)

1. Зарегистрируйтесь на `https://budetege.ru/voyti/` как репетитор
   (адрес из `SEED_TUTOR_EMAIL`) и подтвердите почту.
2. **Сервер: тестовые данные**, режим «создать», в поле подтверждения —
   `ТЕСТ`. В сводке: «„Тестовый класс“: учеников 3; создано аккаунтов 3,
   писем „Сброс пароля“ отправлено 3». Сами адреса в сводке не
   показываются.
3. На каждый адрес ученика придёт письмо «Сброс пароля»: по ссылке из
   него вы задаёте пароль этого ученика.

Тестовые ученики проходят ту же регистрацию, что и настоящие, поэтому их
адреса должны быть в `ALLOWED_EMAILS`. Согласия за них отмечает сама
кнопка: адреса ваши. В обычные «Развернуть» и «Миграции» тестовые
данные не входят. Перед настоящими учениками — та же кнопка в режиме
«удалить».

## Доступ к базе

Порт базы наружу закрыт. Посмотреть таблицы или поправить строку можно
через SSH-туннель: это отдельный пользователь `tunnel` без оболочки, его
ключ умеет только пробросить порт 5432.

1. На компьютере создайте ключ (Terminal / PowerShell):
   `ssh-keygen -t ed25519 -f ~/.ssh/budetege_tunnel`.
2. Содержимое `~/.ssh/budetege_tunnel.pub` (одна строка
   `ssh-ed25519 …`) — в Variable `ADMIN_SSH_PUBLIC_KEY`. Закрытый ключ
   (файл без `.pub`) остаётся только у вас.
3. Придумайте пароль и положите его в секрет `DB_ADMIN_PASSWORD`.
4. Нажмите **Сервер: подготовить** (повторный запуск безопасен: ключ
   добавится) и **Сервер: миграции** (пароль применится).
5. В DBeaver: новое подключение PostgreSQL.
   - **Main:** host `localhost`, порт `5432`, база `postgres`,
     пользователь `budetege_admin`, пароль из шага 3.
   - **SSH:** включить, host — IP сервера, порт 22, пользователь
     `tunnel`, аутентификация — Public key, файл `~/.ssh/budetege_tunnel`.

   Без DBeaver: `ssh -N -L 15432:127.0.0.1:5432 -i ~/.ssh/budetege_tunnel tunnel@IP`,
   потом `psql -h 127.0.0.1 -p 15432 -U budetege_admin postgres`.

`budetege_admin` читает и пишет все таблицы и видит строки всех
аккаунтов, но не суперпользователь. Список аккаунтов:

```sql
select u.email, u.created_at, u.email_confirmed_at, p.display_name, p.role
from auth.users u left join public.profiles p on p.user_id = u.id
order by u.created_at desc;
```

## Если что-то сломалось

Письма приходят с адреса из `SMTP_USER` (по умолчанию
`noreply@budetege.ru`) с темой `[api.budetege.ru] …`. Сначала нажмите
**Сервер: проверить здоровье**: в сводке видно, какой пункт красный.

| Письмо или пункт | Что делать |
|---|---|
| «сервер не отвечает по SSH», «снаружи: … нет ответа» | Панель FirstVDS: сервер включён? Если выключен — включите; контейнеры поднимутся сами. Не помогло — напишите в поддержку FirstVDS. |
| «контейнер … не работает», «GoTrue / PostgREST ответил …» | **Сервер: развернуть** — перезапустит набор, данные не тронет. |
| «сертификат: осталось N дн.» или «Caddy не отдаёт сертификат» | Проверьте, что A-запись `api` указывает на IP сервера. Потом **Сервер: развернуть**. |
| «диск: занято …» | **Сервер: обновить** (чистит старые образы). Не помогло — напишите мне: значит, растёт база или журналы. |
| «память: свободно …», «swap: занято …» | **Сервер: обновить** с отметкой «перезагрузить». Повторяется — пора на тариф с большей памятью: в панели FirstVDS, без переустановки. |
| «Копия не сделана» | **Сервер: копия сейчас** и смотрите ошибку в сводке. Чаще всего это истёкший или удалённый ключ хранилища — создайте новый (шаг 3) и обновите секреты, потом **Сервер: развернуть**. |
| «Восстановление из копии не прошло» | Копии есть, но их нельзя восстановить, или ночные копии перестали делаться. Нажмите **Сервер: копия сейчас**, потом **проверить восстановление**; повторяется — напишите мне. |
| пропали данные, база испорчена | **Сервер: проверить восстановление**, режим «на сервер», в поле подтверждения — `ВОССТАНОВИТЬ`. По умолчанию берётся последняя ночная копия; нужна другая — впишите её имя (список копий — в бакете, папка `budetege-api/daily/`). Перед восстановлением делается копия текущей базы. Сайт без входа на минуту-две. |
| «почта: нет записи SPF» или «нет записи DKIM» | Письма «Подтвердите почту» будут уходить в спам. Откройте Яндекс 360 → домен → DNS-записи и добавьте в DNS на Timeweb то, что он показывает. «ЗАМЕЧАНИЕ почта: записи DMARC нет» — не сбой: добавьте TXT-запись `_dmarc` со значением `v=DMARC1; p=none`, когда будет минута. |
| Регистрация отвечает «Аккаунт не создан» всем, даже адресам из списка | В базе нет текущей редакции документов. Нажмите **Сервер: миграции**: она берёт дату из `app/src/content/legal/operator.json`. |
| «Ключ сервера не совпадает с записанным» | Если вы переустанавливали сервер — удалите секреты `SERVER_KNOWN_HOSTS` и `SERVER_SSH_KEY` и начните с «Подготовить». Если нет — ничего не делайте и напишите провайдеру: кто-то мог подменить сервер. |
| «Подготовить»: `Permission denied, please try again` | Сервер не принял пароль из `SERVER_ROOT_PASSWORD`. Это пароль root из письма о готовности сервера, не пароль от личного кабинета FirstVDS. Сбросить: личный кабинет FirstVDS → Товары → Виртуальные серверы → сервер → **Смена пароля**; новый — в секрет. |
| «Развернуть»: «Порты 80 и 443 заняты, на сервере стоит панель ispmanager» | Нужна чистая Ubuntu без панели — см. «Первый запуск», шаг 1. |
| «Развернуть»: «Порты 80 и 443 заняты, остановить автоматически не могу. Их держит: …» | На сервере программа, которую набор не знает. Пришлите мне эту строку. |
| В журнале письма «Ответ почтового сервера: 535 … Invalid user or password» | Пароль приложения создан не в том ящике, что в `SMTP_USER`. Шаг 2: войдите в нужный ящик, создайте пароль там, проверьте командой из шага 2, обновите `SMTP_PASSWORD`. |
| «Ответ почтового сервера: 535 … does not have access rights to this service» | В ящике из `SMTP_USER` выключены почтовые программы: Почта → настройки → Почтовые программы. |
| «Зеркало пакетов Azure недоступно — …» | Не сбой: машина GitHub сама взяла пакеты Ubuntu с запасного зеркала. |
| «Не удалось поставить на машину GitHub: …» | Не отвечают ни зеркала GitHub, ни серверы Ubuntu. На ваш сервер это не влияет — запустите кнопку позже. |
| Кнопка долго висит «Queued» или кончается `startup_failure` («This run likely failed because of a workflow file issue») | Обычно это сбой самого GitHub Actions — проверьте [githubstatus.com](https://www.githubstatus.com). Когда починят, запустите кнопку новым запуском (Run workflow), а зависшие отмените (Cancel workflow). |

### Переезд на другой сервер

1. Закажите новый сервер. Старый пока не удаляйте.
2. **Сервер: копия сейчас** на старом.
3. В секретах: `SERVER_HOST` и `SERVER_ROOT_PASSWORD` — нового сервера;
   удалите `SERVER_KNOWN_HOSTS` и `SERVER_SSH_KEY`. Ключи шифрования копий
   (`BACKUP_AGE_*`) не трогайте.
4. **Подготовить**, **Развернуть**, **Миграции**, затем **проверить
   восстановление** в режиме «на сервер» с `ВОССТАНОВИТЬ`.
5. Поменяйте A-запись `api` на новый IP. Через час-два, когда **проверить
   здоровье** зелёная, старый сервер можно удалить.

После переезда у сервера новые ключи `anon` и `service_role`. Нажмите
**Сервер: ключ для сайта** (понадобится новый `GH_SECRETS_TOKEN`) и
**Actions → Deploy → Run workflow** — сайт получит новый ключ. Если
нужно перенести старые ключи, — напишите мне, это делается отдельно.

## Как это устроено

```
infra/lite/
  compose.yml, Caddyfile    набор: PostgreSQL 17, GoTrue, PostgREST, Caddy
  compose.ci.yml            только для проверки в CI: Mailpit и S3-сервер
  db/                       роли и схемы Supabase в чистом PostgreSQL, замена Vault
  migrations.txt            какие SQL-файлы применять и в каком порядке
  bin/                      скрипты на сервере: deploy, migrate, seed, backup,
                            restore, health, mail, gen-env, dc
  server/                   подготовка Ubuntu: prepare.sh, настройки, таймеры systemd
  actions/                  шаги кнопок на машине GitHub (ходят на сервер по SSH)
  test/scenario.mjs         сценарий кабинета для проверки в CI
.github/workflows/server-*.yml   кнопки
.github/workflows/lite-server.yml   проверка всего пути в CI
```

На сервере набор лежит в `/opt/budetege-api`:

- `.env.generated` — секреты, созданные на самом сервере при первом
  «Развернуть»: пароли ролей базы, ключ подписи JWT, ключи `anon` и
  `service_role`. Права 600, никуда не копируются;
- `.env.github` — то, что пришло из GitHub Secrets и Variables. Каждое
  «Развернуть» его перезаписывает;
- `state/` — отметки последней копии и писем о проблемах.

**База.** Схема одна — миграции из `supabase/migrations/` по списку
`migrations.txt`: согласия, кабинет (роли, классы, домашние задания),
онлайн-вариант и пробный вход по списку адресов. Каталог банка
(`supabase/seed/kabinet_katalog.sql`) миграцией не является: он
пересобирается вместе с банком и применяется при каждом «Миграции».
Что видит каждая роль — [AUTH.md](AUTH.md), раздел «Что хранится в базе».

**Ключ для сайта.** Публичный ключ `anon` создаётся на сервере и идёт
оттуда прямо в Variables репозитория: кнопка читает его по SSH,
закрывает маской в журнале, сверяет, что роль внутри ключа — именно
`anon`, и записывает через GitHub API. Копировать его руками не нужно.
Сам по себе этот ключ не секрет — его видит любой браузер, открывший
сайт; что по нему доступно, решают правила базы. Секретный ключ
`service_role` с сервера не уходит никуда.

**Кто как входит.** `deploy` — для GitHub Actions: Docker и sudo,
вход только по ключу `SERVER_SSH_KEY`. Это права администратора,
поэтому ключ лежит только в GitHub Secrets. `tunnel` — только туннель к
базе. Вход root и вход по паролю выключены. Повторный вход с неверным
ключом блокирует fail2ban.

**Открытые порты:** 22 (SSH), 80 и 443 (Caddy). База слушает только
127.0.0.1. Docker открывает опубликованные порты в обход ufw, поэтому в
`compose.yml` наружу опубликованы только 80 и 443.

**Копии.** `pg_dump` шифруется открытым ключом age
(`BACKUP_AGE_RECIPIENT`). Закрытый ключ `BACKUP_AGE_IDENTITY` есть только
в GitHub Secrets, поэтому даже с захваченного сервера старые копии не
прочитать. Расшифровывает их машина GitHub при проверке или
восстановлении. Рядом с каждой копией лежит `db-….json` — сколько в ней
аккаунтов, профилей и комплектов. По нему сверяется восстановление.

**Образы Docker** берутся через зеркало `mirror.gcr.io`: Docker Hub
ограничивает число скачиваний с одного адреса. Если скачать не удалось,
а нужные версии уже есть на сервере, «Развернуть» продолжает с ними.

## Как это проверяется

Workflow `lite-server.yml` на каждом pull request с изменениями сервера
берёт чистую машину GitHub (Ubuntu 24.04) и проходит на ней весь путь
теми же скриптами, что и кнопки:

- вход root по паролю → подготовка → вход deploy по ключу → root и
  пароли выключены; ufw, fail2ban, автообновления, swap на месте;
- повторная подготовка ничего не ломает;
- развёртывание с HTTPS (сертификат от собственного центра Caddy вместо
  Let's Encrypt), миграции, повтор миграций;
- миграции единой схемы, каталог банка, редакция документов;
- сценарий пробного кабинета из браузера: 43 проверки — регистрация по
  списку и отказ без согласий, письмо и подтверждение, роль не меняется,
  перенос прогресса, правила доступа «не вижу чужое», аноним, сброс
  пароля, удаление аккаунта — и замер памяти;
- тестовые данные: создать, повторить без дублей, удалить; ключ для
  сайта — это ключ `anon`, и он работает;
- копия в S3, письмо при её сбое, проверка восстановления в пустую базу,
  восстановление на «сервер» — и сверка, что оно не вернуло ролям
  запросов снятые миграциями права;
- проверка здоровья снаружи и изнутри, письмо о проблеме, таймеры systemd;
- туннель к базе: `budetege_admin` входит, оболочки у `tunnel` нет, на
  другие порты туннель не пускает;
- shellcheck всех скриптов и поиск ключей и паролей в репозитории
  (`pnpm test:infra-secrets`).

Чего CI проверить не может: настоящий Let's Encrypt, SMTP Яндекс 360,
Yandex Object Storage и сеть FirstVDS. Их проверят первые нажатия кнопок
на настоящем сервере.
