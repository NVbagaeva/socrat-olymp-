# Оплата через Robokassa

Серверная часть оплаты тарифов. Сайт статический, поэтому подпись
платежа и приём уведомлений об оплате живут на сервере api.budetege.ru,
рядом с базой: сервис `oplata` (`infra/lite/oplata/`) и миграция
`supabase/migrations/20261129120000_oplata.sql`.

## Как идёт оплата

1. Человек на сайте выбирает срок, ставит галочку «Принимаю условия
   оферты» и жмёт «Оформить доступ». Сайт шлёт
   `POST https://api.budetege.ru/oplata/sozdat` с ключом anon
   (`apikey`), входом человека (`Authorization: Bearer <JWT>`) и телом
   `{"tarif": "uchenik", "srok": "d30", "oferta": true}`.
2. Сервис вызывает в базе `oplata_sozdat` **от имени человека**. База
   проверяет роль (ученик берёт «Ученик», учитель — «Учитель»), согласие
   с офертой и предел 20 заказов в час, **сама считает цену** по таблице
   `tarif_tseny` и заводит заказ. Номер заказа — `InvId` для Robokassa.
3. Сервис подписывает ссылку Паролем №1 и отвечает
   `{"url": "https://auth.robokassa.ru/Merchant/Index.aspx?…"}`.
   Сайт переводит человека по этой ссылке.
4. После оплаты Robokassa шлёт уведомление на Result URL
   `https://api.budetege.ru/oplata/result`. Сервис проверяет подпись
   Паролем №2, база (`oplata_zachest`) сверяет сумму с заказом, отмечает
   заказ оплаченным и выдаёт доступ. Ответ Robokassa — `OK<InvId>`.
   Повтор уведомления ничего не меняет и тоже получает `OK`.
5. Человек возвращается на Success URL. Эта страница только сообщает
   результат, доступ по ней не выдаётся.

Срок доступа: «30 дней» — 30 суток от оплаты, «До ЕГЭ» — до конца
30 июня 2027 по Москве (`DO_EGE` в `config.ts`). Новая оплата того же
тарифа продолжает действующий доступ, а не сгорает вместе с ним.
Действующий доступ сайт узнаёт вызовом `rpc/moy_dostup`.

Заказы хранятся и после удаления аккаунта, но без привязки к человеку:
это учёт полученных денег.

## Письма

Письма отправляет рассыльщик (`infra/lite/notifier`) с noreply@budetege.ru,
«Ответить» ведёт на **socratic@budetege.ru** (`POCHTA_VOPROSOV` в
`notifier/pisma.mjs`; другой адрес — переменная окружения `PISMA_REPLY_TO`).
Ученику — на «ты», учителю — на «вы», без «мы» и без рода.

| Письмо | Когда | Кнопка |
| --- | --- | --- |
| «Доступ „Ученик“ открыт 🎉» | сразу после оплаты | «Перейти к занятиям» / «Открыть кабинет» |
| «Доступ „Ученик“ продлён 🎉» | оплата, пока действует прежний срок | то же |
| «Доступ „Ученик“ заканчивается» | за 3 дня до конца последнего срока | «Продлить доступ» → тарифы |

В первом письме — «С чего начать»: как пользоваться сайтом, тренажёр,
варианты онлайн, кабинет (учителю — классы, выдача ДЗ, генератор).
«Заканчивается» не приходит, если следующий срок уже оплачен, и после
«До ЕГЭ» (после экзамена продлевать нечего). Чек — отдельно, от Robokassa.

Очередь — таблица `oplata_pisma`: повтор при сбое почты через 5 минут,
30 минут, 2 часа, после 5 попыток — `failed`.

## Цены

Единственный источник цен — `app/src/lib/tarify/config.ts`. Из него
собирается `supabase/seed/tarify.sql`:

```bash
cd app && pnpm build:tarify-sql
```

Файл применяется при каждом «Сервер: миграции», как каталог банка. CI
(`pnpm test:tarify-sql`) падает, если цены в файле разошлись с
`config.ts`. Поменяли цену — пересоберите файл, влейте в main и нажмите
«Сервер: развернуть» и «Сервер: миграции».

## Настройка магазина в Robokassa

В личном кабинете Robokassa, «Мои магазины» → магазин → «Технические
настройки»:

| Поле                  | Значение                                    |
| --------------------- | ------------------------------------------- |
| Алгоритм хеша         | MD5 (или другой — тогда `ROBOKASSA_HASH`)   |
| Result URL            | `https://api.budetege.ru/oplata/result`     |
| Метод отсылки данных по Result URL | POST (GET тоже принимается)    |
| Success URL           | страница сайта «Оплата прошла»              |
| Fail URL              | страница сайта «Оплата не прошла»           |
| Метод для Success/Fail | GET                                        |

Пароли №1 и №2 придумывает Robokassa или вы — запишите их сразу в
GitHub Secrets (ниже), в чат и в файлы не присылайте. Для тестового
режима у Robokassa **отдельная пара паролей**.

## Секреты и переменные GitHub

Settings → Secrets and variables → Actions.

| Имя                 | Где       | Что                                                        |
| ------------------- | --------- | ---------------------------------------------------------- |
| `ROBOKASSA_PASS1`   | Secrets   | Пароль №1 (подпись ссылки на оплату)                       |
| `ROBOKASSA_PASS2`   | Secrets   | Пароль №2 (проверка Result URL)                            |
| `ROBOKASSA_LOGIN`   | Variables | Идентификатор магазина                                     |
| `ROBOKASSA_HASH`    | Variables | `md5` (по умолчанию), `sha256`, `sha384`, `sha512`, `sha1` — как в настройках магазина |
| `ROBOKASSA_TEST`    | Variables | `1` — тестовый режим (`IsTest=1`, тестовые пароли)         |
| `ROBOKASSA_RECEIPT` | Variables | `1` — передавать состав чека (`Receipt`)                   |

Пока логина или паролей нет, сервис заказов не принимает (503
`oplata_vyklyuchena`). После изменения — «Сервер: развернуть».

**Чек.** Если чек формирует Robokassa (Робочеки, в том числе для
самозанятых — чек уходит в «Мой налог»), уточните в поддержке Robokassa,
нужен ли состав чека в запросе. Если нужен, включите `ROBOKASSA_RECEIPT=1`:
сервис передаст одну позицию — услугу с названием тарифа, без НДС.

## Порядок запуска

1. Магазин в Robokassa создан, технические настройки заполнены, тестовые
   пароли — в Secrets, `ROBOKASSA_TEST=1`.
2. «Сервер: развернуть», затем «Сервер: миграции».
3. Тестовые оплаты: успешная, отказ, повтор. В базе у заказа
   `status = 'oplachen'` и срок `dostup_do`:

   ```sql
   select inv_id, tarif, srok, summa, status, dostup_do
   from public.oplata_zakazy order by inv_id desc limit 10;
   ```

4. Robokassa проверила сайт и перевела магазин в боевой режим: боевые
   пароли — в Secrets, `ROBOKASSA_TEST` убрать, «Сервер: развернуть».
5. Одна реальная оплата на себя, проверить чек.
6. На сайте — `NEXT_PUBLIC_PAYMENTS_ENABLED=1` (`lib/tarify/config.ts`).
