# Как сайт попадает в интернет

Документ для владельца проекта, не для программиста. Читать можно с нуля,
ничего знать заранее не нужно.

Коротко: сайт обновляется сам. Как только изменения попадают в главную ветку
репозитория, GitHub сам собирает сайт и сам загружает его на хостинг. Руками
ничего копировать не надо.

---

## Словарик

Пять слов, которые дальше встречаются постоянно.

**Репозиторий** — хранилище проекта на GitHub. Там лежат все файлы и вся
история изменений.

**Ветка `main`** — главная версия проекта. То, что лежит в `main`, и есть
сайт. Остальные ветки — черновики.

**Pull request** (сокращённо PR, по-русски иногда «пулреквест») — предложение
перенести изменения из черновой ветки в `main`. Пока PR не слит, на сайте
ничего не меняется.

**Workflow** — программа-робот внутри GitHub. Срабатывает сама при заданном
событии и выполняет список шагов. У нас их два.

**Сборка** — превращение исходных файлов проекта в готовые HTML-страницы,
которые умеет показывать браузер. Делается командой, не вручную.

---

## Два робота и чем они отличаются

| | Проверка | Публикация |
|---|---|---|
| Файл | `.github/workflows/check.yml` | `.github/workflows/deploy.yml` |
| Имя в интерфейсе | **Check** | **Deploy** |
| Когда срабатывает | при открытии или обновлении pull request | когда изменения попали в `main` |
| Что делает | собирает сайт и проверяет, что он собирается | собирает сайт **и загружает на хостинг** |
| Трогает ли сервер | **нет, никогда** | да |
| Нужны ли пароли | нет | да |

### Проверка (Check)

Срабатывает, когда вы открываете pull request или дописываете в него что-то
новое. Собирает сайт ровно так же, как это потом сделает публикация, — но
никуда не отправляет. Смысл один: **увидеть поломку до слияния, а не после**.

Что вы увидите на странице pull request, внизу:

- **крутится жёлтый кружок** — проверка идёт, обычно две-четыре минуты;
- **зелёная галочка**, «All checks have passed» — всё собралось, сливать
  можно;
- **красный крестик**, «Some checks were not successful» — что-то сломано.
  Рядом ссылка **Details**, за ней подробности. Кнопка слияния при этом
  не блокируется: GitHub просто предупреждает.

### Публикация (Deploy)

Срабатывает после слияния pull request в `main`. Собирает сайт и загружает
готовые файлы на хостинг Timeweb в папку `/public_html/`.

Есть и ручной запуск, без нового изменения в коде: **Actions → Deploy →
Run workflow**. Пригодится, если, например, поменяли пароль на хостинге
и хотите перезалить то же самое.

### Загрузка только добавляет файлы

Важное свойство, ради которого настройка делалась отдельно. Публикация
**никогда не удаляет** с сервера то, чего нет в сборке. Папка `ege`
со стереометрией, `about.html` и остальные старые страницы останутся на
месте, что бы ни происходило со сборкой.

Единственный режим, способный стереть содержимое папки на сервере,
называется `dangerous-clean-slate`, и он выключен явным образом, с
комментарием в файле. Не включайте его.

## Пароли от хостинга

Пароли не лежат в коде — иначе их увидел бы каждый, у кого есть доступ к
репозиторию. Они хранятся в защищённом разделе GitHub и подставляются
роботу в момент работы.

**Где лежат:** Settings → Secrets and variables → **Actions** → вкладка
**Secrets**.

| Название | Что внутри |
|---|---|
| `FTP_SERVER` | адрес сервера, вида `cz903519.tw1.ru`. Без `ftp://` в начале и без пути в конце |
| `FTP_USERNAME` | логин FTP, вида `cz903519_socrat` |
| `FTP_PASSWORD` | пароль от этого логина |

Названия должны совпадать до буквы — робот ищет их именно так.

Посмотреть уже сохранённое значение нельзя, даже вам: GitHub показывает
только название. Можно лишь заменить на новое. Это не поломка, а защита.

Если пароль на хостинге меняется, его нужно заменить и здесь, иначе
публикация начнёт падать.

## Почему подключение незашифрованное

В настройках публикации стоит `protocol: ftp` и `port: 21` — обычный FTP,
без шифрования, на стандартном порту. Это выглядит небрежно, поэтому объясню,
как мы к этому пришли.

Сначала стояло `ftps` — тот же FTP, но с шифрованием. Сервер отвечал ошибкой
`530 Please login with USER and PASS`. Подумали на строгость режима
шифрования, попробовали второй его вариант, `ftps-legacy`. Тоже мимо.

Разгадка нашлась при проверке обычной программой FileZilla: подключение
проходит, логин и пароль верные, каталоги видны — но FileZilla прямо
предупреждает: **«Небезопасный сервер, не поддерживает FTP через TLS»**.

То есть сервер Timeweb на этом тарифе не умеет шифрование **вообще**. Дело
было не в том, какой режим выбрать, а в том, что выбирать не из чего.
Поэтому `protocol: ftp` — не упрощение, а единственный вариант, который
сервер принимает.

### Что это означает на практике

**Логин, пароль и содержимое файлов уходят на сервер открытым текстом.**
Любой, кто может прослушать сеть между GitHub и Timeweb, увидит их целиком.
Это свойство самого протокола, настройками не лечится.

Отсюда два правила:

1. **Считайте пароль от FTP скомпрометированным.** Не потому, что его уже
   украли, а потому, что он ходит по сети открыто и мы этого не контролируем.
2. **Нигде больше этот пароль не используйте.** Ни для почты, ни для панели
   хостинга, ни для чего-либо ещё. Он должен быть уникальным и ничего, кроме
   загрузки файлов на сайт, не открывать.

Ничего секретного в самих файлах нет — это публичные страницы сайта, их и
так видит любой посетитель. Рискует только пароль.

### Что делать при переезде на VDS

Когда проект переедет с общего тарифа на отдельный сервер (VDS), первым
делом нужно **перейти с FTP на SFTP**.

SFTP — это передача файлов поверх SSH. Название похоже на FTP, но это другой
протокол: шифруется всё, включая вход. На VDS SSH есть всегда, поэтому
ограничение, из-за которого мы сидим на открытом FTP, исчезнет само.

Что для этого понадобится:

- завести на сервере отдельного пользователя для публикации;
- вместо пароля использовать SSH-ключ — это надёжнее и удобнее;
- заменить в `deploy.yml` шаг загрузки: действие `SamKirkland/FTP-Deploy-Action`
  с SFTP не работает, нужно другое;
- после переезда старый FTP-пароль отозвать.

Отдельная задача, заранее её делать не нужно. Но при планировании переезда
её стоит держать в списке.

## Если публикация упала

Открываете **Actions**, сверху — упавший запуск с красным крестиком. Внутри
список шагов, упавший помечен красным и раскрыт. Два случая ниже покрывают
почти всё, что реально случается.

### Случай 1. Ругается на лок-файл

**Как выглядит.** Падает шаг «Поставить зависимости», в логе:

```
ERR_PNPM_OUTDATED_LOCKFILE
Cannot install with "frozen-lockfile" because pnpm-lock.yaml
is not up to date with package.json
```

**Что произошло.** В проект добавили новую библиотеку, но не обновили файл
со списком точных версий (`pnpm-lock.yaml`). Робот отказывается додумывать
версии сам — иначе сборка перестала бы быть предсказуемой.

**Что делать.** Открыть PowerShell и выполнить одной строкой, подставив свой
путь к проекту:

```powershell
cd C:\путь\к\socrat-olymp-\app; git checkout main; git pull; pnpm install; git add pnpm-lock.yaml; git commit -m "Обновить лок-файл"; git push
```

По шагам, если хочется понимать:

1. `cd …\app` — перейти в папку проекта (именно в `app`, не в корень);
2. `git checkout main` — переключиться на главную ветку;
3. `git pull` — забрать свежую версию с GitHub;
4. `pnpm install` — обновить список версий;
5. `git add pnpm-lock.yaml` — отметить изменённый файл к отправке;
6. `git commit -m "…"` — сохранить изменение с подписью;
7. `git push` — отправить на GitHub.

Последний шаг сам запустит публикацию заново. Ждать и нажимать ничего не надо.

### Случай 2. Ругается линтер

**Как выглядит.** Падает шаг «Собрать статический экспорт», в логе строки
вида:

```
./src/lib/graph/solution.js
67:10  Error: 'note' is assigned a value but never used.
```

**Что произошло.** Линтер — это автоматический редактор-придира. Он читает
код и указывает на подозрительное: объявили переменную и не воспользовались,
забыли убрать черновой кусок. Ошибки линтера останавливают сборку намеренно:
как правило, такая находка означает недоделанную правку.

**Что делать: ничего не удалять самой.** Нужно разобраться, почему код не
используется, и вариантов два. Либо это забытый мусор — тогда его убирают.
Либо логика не дописана — и тогда удаление замаскирует настоящую ошибку.

Отличить одно от другого по логу нельзя, нужно смотреть код. Это работа
разработчика или Claude Code.

Как читать сообщение:

- `./src/lib/graph/solution.js` — в каком файле;
- `67:10` — строка 67, символ 10;
- текст после `Error:` — суть претензии.

Скопируйте эти строки целиком и передайте их тому, кто будет чинить. По ним
причина находится сразу.

Реальный пример из этого проекта: линтер отметил шесть неиспользуемых
переменных. Пять оказались мусором и были удалены. Шестая — импортом, который
случайно перекрыла функция с тем же именем, из-за чего формулы в разборе
задач не отображались вообще. Удали её тогда «за ненадобностью» — поломка
осталась бы навсегда и искали бы её месяцами.

### Если упало где-то ещё

Скопируйте название упавшего шага и последние 20–30 строк лога. Этого хватит,
чтобы разобраться. Гадать по памяти не нужно — в логе написано всё.

## Что здесь описано на будущее

Настройка сложилась не сразу, и большинство граблей уже пройдено. Сводка на
случай, если что-то похожее повторится:

- **зависимости ставятся строго по лок-файлу** (`--frozen-lockfile`).
  Это сделано намеренно: так сборка сегодня и через год даёт одинаковый
  результат. Цена — случай 1 выше;
- **сборка выполняется дважды** — один раз на pull request, второй после
  слияния. Так задумано: первая проверяет, вторая публикует;
- **загрузка только добавляет**, ничего не удаляет;
- **шифрования нет**, и это ограничение хостинга, а не недосмотр.
